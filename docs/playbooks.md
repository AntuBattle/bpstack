# Playbook guide

Choose the playbook by the outcome you need, not by the files you expect to edit. These 24 playbooks cover diagnosis, implementation, delivery, and session handoff. Use this guide to route a task; read the linked playbook in full before executing it.

## Using a playbook

1. Start with [Poteto Mode](../skills/poteto-mode/SKILL.md). Pick one primary playbook and add shared helpers only when they apply. For large cross-cutting work with no safe fit, use [Figure It Out](../skills/figure-it-out/SKILL.md) to define a custom plan with a proof for each unit.
2. Keep a short execution checklist. Load supporting skills when they change a concrete decision. Mark omitted applicable steps as `skip: <reason>` and say what remains unverified.
3. Check available capabilities against the [portability contract](../PORTABILITY.md). Sequential self-review is not independent review; a build is not a runtime check. Test locally first with external services mocked at their boundaries. Use shared or potentially production services only with authorization for the current task; never run write or destructive tests on a non-isolated service. See [Prove It Works](../skills/principle-prove-it-works/SKILL.md).

## Diagnose and measure

Use **investigation** for a read-only answer, **runtime forensics** for a symptom you need to observe live, and **trace forensics** when the captured artifact is your evidence. A **performance issue** targets a specific slow path; a **metric hillclimb** keeps iterating toward a measurable target.

| Playbook | Use when | How the agent works | Expected evidence or output |
| --- | --- | --- | --- |
| [Read-only investigation](../skills/poteto-mode/playbooks/investigation.md) | You need to know why a subsystem behaves as it does, or whether a proposed change belongs in it. | Sync checkouts by fetch and fast-forward before reading code when authorized; confirm any branch other than `main` or `master` before relying on it. For scope questions, run [Broader Scope Analysis](../skills/broader-scope-analysis/SKILL.md) and record the pre-diff baseline first. Trace the relevant path with [How](../skills/how/SKILL.md) and try to disprove the leading explanation. | Direct answer with concrete files, revisions, commands, or other inspected evidence. Distinguish observation from inference and name gaps. |
| [Runtime forensics](../skills/poteto-mode/playbooks/runtime-forensics.md) | A live process stalls or misbehaves and existing evidence cannot distinguish the causes. | Observe the shortest useful window, use the least invasive probes, align events on one timeline, and try a counterfactual or controlled perturbation where possible. Do not turn diagnosis into a fix without authorization. | Timeline, causal diagnosis with a confidence level, and the counter-check result or its limitation. |
| [Captured trace forensics](../skills/poteto-mode/playbooks/trace-forensics.md) | You have a trace, profile, or recording and need to explain what it shows. | Validate the capture environment, clock, and completeness. Examine dominant intervals, stacks, allocations, waits, or event clusters. Check the leading explanation against another trace or a source-level prediction when available. | Diagnosis tied to trace locations, uncertainty, and the next measurement that would distinguish remaining explanations. |
| [Performance issue](../skills/poteto-mode/playbooks/perf-issue.md) | A particular operation is slow or expensive and you want to fix the dominant cost. | Baseline a user-visible metric under controlled conditions, profile the actual path, and test the smallest change implied by one hypothesis. Remeasure under the same conditions; reject cost-shifting and regressions. | Before/after numbers, measurement environment, traces used, and remaining bottlenecks. |
| [Metric hillclimb](../skills/poteto-mode/playbooks/hillclimb.md) | You want to move a metric toward a defined target through multiple experiments. | Set the metric, target, guardrails, and repeatable benchmark; save the baseline. Test ranked hypotheses one variable at a time. Keep only measured wins that pass the guardrails, each in its own reversible checkpoint. | Benchmark command, baseline, accepted and rejected trials with results, and the reason the run stopped. |

## Build, change, and evaluate

Use a **feature** to change what a consumer can do, a **bug fix** to restore expected behavior, and a **refactor** to preserve behavior while changing structure. Use a **prototype** when the next deliverable is a decision rather than production code.

| Playbook | Use when | How the agent works | Expected evidence or output |
| --- | --- | --- | --- |
| [Bug fix](../skills/poteto-mode/playbooks/bug-fix.md) | Observed behavior differs from the contract or a previously working flow. | Reproduce the failure, trace [the root cause](../skills/principle-fix-root-causes/SKILL.md), and capture a failing behavior-level check when practical ([TDD](../skills/tdd/SKILL.md)). Fix the cause with minimal scope, re-run the reproduction, and use [Review and verify](#review-and-verify). If reproduction fails, gather evidence rather than guess. | Exact observed vs. expected behavior, cause, focused patch, regression and local verification results, and any unavailable surfaces. |
| [Feature](../skills/poteto-mode/playbooks/feature.md) | You need a new user-visible outcome or state transition. | Define the outcome, data shape, and scope of one verifiable slice. Inspect existing callers and test paths, settle new contracts with [Architect](../skills/architect/SKILL.md), and implement the smallest end-to-end slice. Use [Review and verify](#review-and-verify). | Working slice with explicit acceptance criteria, targeted and relevant broader checks, local end-to-end evidence when applicable, and review results. |
| [Refactoring](../skills/poteto-mode/playbooks/refactoring.md) | You want to simplify structure or replace an internal API without changing behavior. | Capture a behavior baseline, map affected callers and boundaries with [Blast Radius](../skills/blast-radius/SKILL.md), and prefer direct simplification over new compatibility layers. [Migrate callers before deleting old internal APIs](../skills/principle-migrate-callers-then-delete-legacy-apis/SKILL.md). | Before/after proof of the same observable behavior, broader checks for affected callers, and any unresolved gaps. Behavior drift is a bug. |
| [Prototype](../skills/poteto-mode/playbooks/prototype.md) | Evidence, not preference, can settle a design choice. | Write the decision criteria first. Build the cheapest faithful sketch; compare two or three materially different variants for a contested choice. Observe them on the closest meaningful surface and compare costs that would persist in production. See [Exhaust the Design Space](../skills/principle-exhaust-the-design-space/SKILL.md). | Recommendation or rejection tied to observed results. Delete or quarantine throwaway code unless asked to keep it. |
| [Visual parity](../skills/poteto-mode/playbooks/visual-parity.md) | A UI must match a reference design or previous rendering within an agreed tolerance. | Fix viewport, fonts, data, theme, scale, and animation state. Capture both on the same surface, compare geometry before visual details, and recapture after changing one causal layout or style cluster. | Comparable captures, overlays or pixel measurements where available, and results across the required states. Report exact remaining differences if pixel proof is blocked. |
| [Authoring a skill](../skills/poteto-mode/playbooks/authoring-a-skill.md) | You need reusable agent instructions for a recurring task. | Define triggers, non-triggers, outcomes, and capability fallbacks. Keep `SKILL.md` focused and move bulky examples or utilities to supporting files. Validate metadata and directory/name parity, then exercise positive and negative cases. | Portable skill package with validation results and examples showing that it activates and behaves as intended. |
| [Skill or prompt evaluation](../skills/poteto-mode/playbooks/eval.md) | You need to decide whether a revised prompt or skill is better than the baseline. | Freeze candidates, rubric, guardrails, and representative tasks before judging. Compare under equivalent models, tools, context, and budgets; blind or randomize judging when practical. Score outcomes and inspect regressions individually. | Preserved inputs, outputs, scores, regressions, and a promotion decision tied to the primary metric and guardrails. |

## Plan, coordinate, and deliver

Use **multi-phase work** to sequence one migration, **autonomous run** to execute against clear completion criteria, and **project orchestration** for a program with multiple owners or milestones. Use the **independent PR autopilot** for separate changes and the **linear stack autopilot** for changes that depend on each other. **Babysit** makes an existing PR merge-ready; **shipping** lands verified work when authorized.

| Playbook | Use when | How the agent works | Expected evidence or output |
| --- | --- | --- | --- |
| [Multi-phase work](../skills/poteto-mode/playbooks/multi-phase-plan.md) | A migration or rewrite needs several separately verifiable transitions. | Define the target state and acceptance gates. Name temporary states and specify each phase's inputs, changes, proof, dependencies, and rollback or checkpoint. Verify one phase before starting the next; re-plan when evidence changes. See [Sequence Verifiable Units](../skills/principle-sequence-verifiable-units/SKILL.md). | Ordered plan with proof and rollback per phase; verified checkpoints and an updated plan if execution is in scope. |
| [Autonomous run](../skills/poteto-mode/playbooks/autonomous-run.md) | You want the agent to keep working within agreed bounds until a concrete result is achieved. | Define completion and irreversible-action boundaries. Execute the highest-leverage verifiable unit, verify it, checkpoint it, and recompute the queue. Keep a [decision trail](../skills/show-me-your-work/SKILL.md); stop for completion, a real blocker, or a decision requiring human authority. | Completion proof or exact stop condition, plus verified checkpoints and the next actionable unit if unfinished. |
| [Project orchestration](../skills/poteto-mode/playbooks/orchestrate.md) | Several workstreams share interfaces, dependencies, or an integration target. | Define milestone gates and integration state, give each slice one owner, and minimize shared mutable state. Delegate isolated slices where possible; inspect artifacts and evidence and require owner-independent review before integration. Disclose any loss of independence. | Milestone and dependency map, durable integration log, slice evidence, and integrated proof at milestone and program level. |
| [Independent PR autopilot](../skills/poteto-mode/playbooks/autopilot-full.md) | You have a queue of independently landable PRs or changes. | Assign one owner and merge criteria per item. Require an independent verdict for the exact head and matching current PR state before an authorized landing. Reconcile the base and recheck queued items after each merge. | Per-item head, verification verdict and current PR state, landed revisions, and any invalidated assumptions or blockers. |
| [Linear stack autopilot](../skills/poteto-mode/playbooks/autopilot-stack.md) | You need a coherent stack of dependent changes, with each layer reviewable on its own. | Build each layer on the verified previous layer, avoid parallel edits to shared stack state, and fix failures at the lowest responsible layer. Deliver the reviewed stack without landing unless shipping was explicitly requested. | Stack order, exact head revisions, per-layer proof, and assumptions to check before landing. |
| [Drive a PR to merge-ready](../skills/poteto-mode/playbooks/babysit.md) | An open PR has failing checks, conflicts, or unresolved feedback. | Inspect the head, review threads, conflicts, and CI first. Classify each blocker, resolve one at a time, re-run the necessary checks, and refresh PR status. Green CI alone does not establish merge readiness. | Merge-ready verdict or precise external blocker, with status of outstanding threads, conflicts, and checks. |
| [Verify and ship](../skills/poteto-mode/playbooks/shipping.md) | You are authorized to land one or more reviewed changes. | Freeze exact heads and independently verify acceptance criteria in dependency order. Land bottom-up only through the longest verified run from the root. After each landing, recheck the next head and base against what was verified. | Landed revisions, exact heads verified, and the first stop condition if part of the stack could not land. |

## Resume, pause, and clean up

| Playbook | Use when | How the agent works | Expected evidence or output |
| --- | --- | --- | --- |
| [Session pickup](../skills/poteto-mode/playbooks/session-pickup.md) | You are resuming work and need to establish which earlier claims still hold. | Use [Recall](../skills/recall/SKILL.md) to recover branch and diff, decision records, issue or PR state, and test outputs before relying on a transcript. Re-run the smallest proof for the current head, then reconstruct the next unit from that state. | Updated handoff with current revision, verified facts, unsupported claims or gaps, and the next verifiable unit. |
| [Pause safely](../skills/poteto-mode/playbooks/pause-safely.md) | You need to stop in-progress work without leaving a partial operation or an armed external action. | Stop starting new work; finish or revert half-applied local operations. Record the branch, worktree, dirty files, running jobs, external state, decisions, and last verified checkpoint. Run the cheapest coherence check. | Pickup note with sanity-check result, exact next action, and anything that must not be repeated. |
| [Worktree and local-state cleanup](../skills/poteto-mode/playbooks/worktree-cleanup.md) | You want to remove stale checkout state or reclaim disk space safely. | Inventory worktrees, branches, dirty state, unpushed commits, processes, and related caches. Preview the exact prune set and check dependencies before deleting only proven-safe items. Preserve unknown state. | Before/after inventory, what was removed and preserved, and space reclaimed. |

## Shared helpers

### Review and verify

Use [Review and verify](../skills/poteto-mode/playbooks/review-and-verify.md) for every feature and bug fix, including minor patches. It supplements, rather than replaces, targeted checks and the original bug reproduction.

- **Before implementation:** Review shape early when a proposal changes ownership, shared state, an interface, or a significant abstraction. Use an isolated reviewer if available and resolve major findings before editing.
- **After targeted checks:** For every behavior change, run the actual app locally in isolation and drive the changed behavior through its normal UI, CLI, or API. Use an existing verification skill or harness when available. Mock external services, not the path under test. Record steps, expected and observed results, mocks, and any automation gap; clean up afterward. If local end-to-end verification is impossible or inapplicable, record the reason and what remains unverified.
- **Before handoff:** Run the shape, code, and intent reviews in order against the same unchanged diff and its evidence. Check that the change is in the right layer, the implementation and tests are sound, and the result meets the original request. Use a fresh, isolated reviewer per lens when available, or label sequential self-review as non-independent. If a major issue is found, fix it or show why it does not block, then repeat the review round. Re-run affected checks after edits. Report verification and review results, and block on unresolved major findings.

### Opening a PR

Use [Opening a PR](../skills/poteto-mode/playbooks/opening-a-pr.md) when the task calls for a new PR, whether directly or as an implementation handoff. It is not permission to merge. Review the full diff for scope and record the exact checks and results. Write a concise description covering impact, the root cause or design choice, and verification. Follow repository title conventions; otherwise prefer `type(scope): summary`.

**PR gate for behavior-changing work:** Open a ready-for-review PR only after the required checks pass and evidence verifies the changed behavior on the exact candidate. If verification fails or cannot be completed, report the blocker and what remains unverified instead of opening a PR. Open a draft only if the user explicitly requested one and publishing is authorized; describe the verification gap in the draft. A draft does not clear the gate.

When authorized to publish, use the available VCS host, refresh status once, and report the real PR link or identifier along with any immediate blocker.
